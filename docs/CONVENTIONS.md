# Engineering & Telemetry Conventions (Synusia FARO V3)

This document establishes the project-wide standards for casing, naming conventions, and domain vocabulary.

---

## 1. Casing Rules

| Layer                                       | Standard           | Examples                                                                |
| :------------------------------------------ | :----------------- | :---------------------------------------------------------------------- |
| **Database Tables & Columns**               | `snake_case`       | `id_equip`, `telemetry_logs`, `is_evidence_cited`, `moment_b_seguretat` |
| **JSON Payload Fields (`metrics_payload`)** | `snake_case`       | `tokens_used`, `latency_ms`, `prompts_count`, `nom_equip`               |
| **TypeScript Variables & Functions**        | `camelCase`        | `promptsCountCurrent`, `desarMetriquesFase`, `momentAConfidence`        |
| **TypeScript Types, Interfaces & Schemas**  | `PascalCase`       | `TelemetryPayload`, `ChatRequestBody`, `ConfidencePayloadSchema`        |
| **Global Constants & Enums**                | `UPPER_SNAKE_CASE` | `CANONICAL_MISSIONS`, `CANONICAL_EVENT_TYPES`                           |

---

## 2. Strict Domain Dictionary

### Missions

All mission identifiers must be normalized using `normalizeMissionId()`. Never pass bare integers (`0`, `1`) or alternative formats (`fase_1`) into the database.

- `MISION_1`
- `MISION_2`
- `MISION_3`
- `MISION_4`

### Telemetry Actors

- `OPERATOR`: Human learner interaction.
- `IA_BOT`: In-character conversational agent responses.
- `SYSTEM`: System messages, orchestrations, or internal fallback warnings.

### Telemetry Event Types

- `PROMPT_SUBMISSION`: A prompt sent by the student.
- `RESPOSTA_IA`: Standard response generated by the LLM.
- `MILESTONE_COMPLETED`: Mission phase cleared (victory condition met).
- `HURDLE_TRIGGERED`: Input stopped by guardrails (jailbreak, empty/vague input).
- `CONFIDENCE_PROBE`: Modal ratings captured at Phase start (`MOMENT_A`) or end (`MOMENT_B`).

---

## 3. Architecture Boundary Rules

1. **Client Isolation:** React components (frontend) are forbidden from inserting rows directly into `telemetry_logs` or `logs_interaccio` via the Supabase client.
2. **Gateway:** All telemetry, metrics, and LLM chat requests must execute through server endpoints (`/api/chat`, `/api/telemetry/confidence`) using `supabaseAdmin` with the `SERVICE_ROLE_KEY`.
3. **Validation:** Every inbound API body must be parsed through a Zod schema before executing database operations or external API calls.
